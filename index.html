CHAPTER 01 · CORE CONCEPT

Render و Commit چه تفاوتی دارند؟

وقتی React یک کامپوننت را Render می‌کند، یعنی برای محاسبه UI مورد نیاز، تابع کامپوننت را اجرا می‌کند. این کار به معنی تغییر فوری صفحه نیست.

در Commit، React تغییرات لازم را روی محیط مقصد، مثل DOM، اعمال می‌کند. ممکن است یک کامپوننت دوباره Render شود اما خروجی قابل‌نمایش تغییری نکرده باشد.

نکته طلایی
Re-render ≠ DOM update
اجرای دوباره کامپوننت الزاماً به معنی تغییر DOM نیست.

برای مثال، اگر محتوای دکمه قبل و بعد از Render همچنان «Count: 1» باشد، React ممکن است نیاز به تغییر متن دکمه در DOM نداشته باشد.

سه اصطلاح که نباید با هم قاطی شوند

مفهومچه کسی انجام می‌دهد؟نتیجه
RenderReactفراخوانی کامپوننت و محاسبه توصیف جدید UI
CommitReact و renderer مربوطاعمال تغییرهای لازم در DOM و اجرای چرخه‌های مربوط به Commit
Paintمرورگررسم پیکسل‌ها در زمان مناسب؛ ممکن است بعد از Commit رخ دهد
نکته ظریف: وجود یک Commit الزاماً یعنی DOM تغییر کرده نیست. ممکن است React کاری را Commit کند ولی تغییر قابل‌مشاهده‌ای روی DOM نباشد. همین‌طور آپدیت State به مقدار قبلی، گاهی پیش از Render جدید کنار گذاشته می‌شود.
UNDER THE HOOD

از تغییر State تا نمایش نتیجه

این مدل ساده‌شده به ما کمک می‌کند جریان آپدیت را در ذهن نگه داریم:

۱. Updateثبت درخواست آپدیت State
۲. Renderمحاسبه UI جدید و تطبیق آن
۳. Commitاعمال تغییرات لازم در DOM

بعد از Commit، مرورگر در زمان مناسب می‌تواند نتیجه را Paint کند. نکته مهم این است که Reconciliation بخشی از فرایند Render است و لزوماً یک مرحله کاملاً جداگانه بعد از آن نیست.

UNDER THE HOOD · DEEP DIVE

Reconciliation و Fiber دقیقاً چه می‌کنند؟

React از خروجی JSX یک توصیف از عناصر می‌سازد. برای اینکه بداند چه چیزهایی باید نگه داشته، تغییر داده یا حذف شوند، درخت جدید را با وضعیت قبلی تطبیق می‌دهد؛ به این فرایند Reconciliation می‌گوییم. این کار در فاز Render انجام می‌شود و خودش به‌معنی دست‌زدن به DOM نیست.

Fiber چیست؟

Fiber ساختار داخلی React برای نگهداری اطلاعات کارِ هر بخش از درخت و امکان زمان‌بندی آن است. به زبان ساده، React می‌تواند روی بخش‌هایی از کار Render قدم‌به‌قدم پیش برود. در رندرهای concurrent، ممکن است کار کم‌اولویت را متوقف کند، دوباره شروع کند یا کنار بگذارد؛ اما خروجی نیمه‌کاره را Commit نمی‌کند.

Render باید خالص باشد

تابع کامپوننت بهتر است از ورودی‌های یکسان خروجی یکسان بدهد و هنگام Render کار جانبی مثل درخواست شبکه یا تغییر DOM انجام ندهد.

Commit اتمیکِ قابل مشاهده است

React یک خروجی نهایی سازگار را Commit می‌کند؛ نه چند وضعیت نیمه‌تمام از کار Render متوقف‌شده را.

چرا identity و key مهم هستند؟

React برای تشخیص حفظ یا جایگزینی یک کامپوننت به نوع عنصر و موقعیت آن در درخت و در لیست‌ها به key توجه می‌کند. وقتی identity عوض شود، State محلی ممکن است از نو ایجاد شود. key فقط برای ساکت کردن warning نیست؛ مشخص می‌کند کدام آیتم کدام است.

STATE MODEL

State Snapshot و Automatic Batching

هر بار که React کامپوننت را Render می‌کند، مقدارهای State و handlerهای آن Render یک snapshot می‌سازند. اجرای setter متغیر جاوااسکریپتی همان handler را عوض نمی‌کند؛ یک درخواست برای Render آینده ثبت می‌کند.

دو الگوی آپدیت که نتیجه متفاوت دارند

const handleClick = () => {
  setCount(count + 1);
  setCount(count + 1);
  setCount(prev => prev + 1);
};

اگر count در این handler برابر صفر باشد، دو درخواست اول هر دو مقدار 1 را صف می‌کنند؛ آپدیت تابعی سوم مقدار در حال پردازش را یکی افزایش می‌دهد. نتیجه بعد از پردازش صف ۲ خواهد بود، نه ۳.

قاعده ذهنی: وقتی مقدار بعدی به مقدار قبلی وابسته است، از فرم تابعی setCount(c => c + 1) استفاده کن؛ به‌خصوص وقتی چند آپدیت پشت سر هم داری.

Automatic Batching در React 18+

با استفاده از createRoot، React معمولاً آپدیت‌های یک دسته از callbackها، از جمله Promise و setTimeout را نیز با هم batch می‌کند؛ یعنی تعداد Renderهای لازم را کاهش می‌دهد. Batching باعث نمی‌شود متغیر snapshot در handler ناگهان عوض شود. flushSync یک ابزار استثنایی برای نیازهای خاصِ همگام‌سازی است، نه راه‌حل پیش‌فرض.

آپدیت‌های چند رویداد مستقل کاربر مثل دو کلیک جدا، بی‌قیدوشرط در یک batch واحد ادغام نمی‌شوند.

COMPONENT TREE

چرا Render والد می‌تواند روی فرزند اثر بگذارد؟

وقتی والد دوباره Render می‌شود، React به‌طور معمول مسیر فرزندان را هم بررسی می‌کند و ممکن است تابع آن‌ها را دوباره اجرا کند؛ حتی اگر propهای قابل مشاهده‌شان ظاهراً ثابت باشد. React.memo در شرایط مناسب می‌تواند از Render غیرضروری یک فرزند جلوگیری کند؛ ولی تضمین مطلق نیست، چون State خود فرزند یا Context مصرف‌شده همچنان ممکن است آن را آپدیت کند.

const HotelCard = React.memo(function HotelCard({ name }: { name: string }) {
  console.log('HotelCard render');
  return <article>{name}</article>;
});

function HotelPage() {
  const [filter, setFilter] = useState('');
  return <>
    <input value={filter} onChange={e => setFilter(e.target.value)} />
    <HotelCard name="Example Hotel" />
  </>;
}

در این مثال، با تغییر فیلتر، والد Render می‌شود؛ اما HotelCard چون prop ثابت دارد و با memo پوشیده شده، معمولاً می‌تواند Render خود را رد کند. برای تصمیم درباره بهینه‌سازی، قبل از اضافه‌کردن memo حتماً با Profiler اندازه‌گیری کن.

سناریوی واقعی هتل: وقتی فیلتر لیست هتل تغییر می‌کند، لازم نیست هر کارت گران‌قیمت دوباره محاسبه شود؛ اما راه‌حل صرفاً پاشیدن memo روی همه کامپوننت‌ها نیست. identity propها، Context و طراحی State اهمیت دارند.
LIFECYCLE TIMING

Effectها دقیقاً کِی اجرا می‌شوند؟

در React، Render برای محاسبه UI است و Effectها برای هماهنگ‌کردن کامپوننت با سیستم‌های بیرونی، مثل subscription، کتابخانه نقشه یا اتصال شبکه هستند. زمان اجرا به نوع Effect و شرایط رندر بستگی دارد.

  1. Render Phaseمحاسبه خروجی UI؛ باید بدون side effect باشد.
  2. Commit Phaseبه‌روزرسانی‌های لازم DOM و مراحل مربوط به layout effect.
  3. Browser Paintمرورگر در فرصت مناسب فریم را نمایش می‌دهد؛ زمان Paint همیشه یک خط ثابت نیست.
  4. Passive EffectsuseEffect معمولاً پس از Paint اجرا می‌شود، ولی در بعضی تعامل‌ها زمان‌بندی می‌تواند متفاوت باشد.
useLayoutEffect

برای خواندن layout و اعمال اصلاح لازم قبل از Paint مناسب است؛ استفاده سنگین از آن می‌تواند نمایش صفحه را عقب بیندازد.

useEffect

برای اتصال به سیستم بیرونی مناسب است و معمولاً نباید برای محاسبه داده‌ای که در Render قابل محاسبه است استفاده شود.

Strict Mode در Development

در حالت توسعه، Strict Mode می‌تواند اجرای اضافه کامپوننت و چرخه setup/cleanup مربوط به Effect را برای آشکارکردن باگ‌های ناخالصی و cleanup ناقص انجام دهد. این رفتار را نباید به‌اشتباه به‌عنوان تعداد Renderها در Production تعبیر کرد.

CODE LAB

یک مثال خیلی ساده

function Counter() {
const [count, setCount] = useState(0);
console.log('render', count);

return (
<button onClick={() => setCount(c => c + 1)}>
{count}
</button>
);
}

با هر کلیک، یک آپدیت State درخواست می‌شود. React مقدار جدید را در Render بعدی محاسبه می‌کند و اگر متن دکمه عوض شده باشد، تغییر لازم را Commit می‌کند.

دقت کن: دیدن console.log('render') فقط به ما می‌گوید تابع کامپوننت اجرا شده؛ به‌تنهایی ثابت نمی‌کند DOM هم تغییر کرده است.

آزمایش اول: آیا setter فوراً State را تغییر می‌دهد؟

function SnapshotDemo() {
  const [count, setCount] = useState(0);
  const click = () => {
    setCount(count + 1);
    console.log('inside handler:', count);
  };
  console.log('render:', count);
  return <button onClick={click}>{count}</button>;
}

از مقدار صفر شروع کن. داخل handler همچنان صفر log می‌شود، چون handler از snapshot رندر قبلی استفاده می‌کند. در Render بعدی عدد ۱ به تابع داده می‌شود و متن دکمه در صورت نیاز تغییر می‌کند.

آزمایش دوم: آیا هر Render به تغییر DOM نیاز دارد؟

function Parent() {
  const [tick, setTick] = useState(0);
  return <>
    <button onClick={() => setTick(t => t + 1)}>Parent: {tick}</button>
    <Child label="unchanged" />
  </>;
}
function Child({ label }: { label: string }) {
  console.log('Child called');
  return <p>{label}</p>;
}

فرزند ممکن است دوباره اجرا شود، اما متن unchanged در DOM نیازی به تغییر ندارد. اگر بخواهی این تفاوت را اندازه‌گیری کنی، React DevTools Profiler از شمارش صرفِ console.log مناسب‌تر است.

COMMON MISTAKES

دو سوءبرداشت رایج

«هر بار setState می‌زنم، همان لحظه مقدار State تغییر می‌کند» — نه؛ مقدار State در handler مربوط به snapshot همان Render است.

«هر بار کامپوننت Render می‌شود، مرورگر دوباره تمام صفحه را می‌سازد» — نه؛ React تغییرات لازم را تعیین می‌کند و مرورگر هم چرخه رندر خودش را دارد.

سؤال‌های مصاحبه

طبق روشی که با هم توافق کردیم، هنوز مرحله سؤال و جواب شروع نشده. این‌ها نمونه‌هایی هستند که بعد از تسلط مفهومی به‌ترتیب بررسی می‌کنیم.

چرا اجرای دوباره یک کامپوننت الزاماً DOM را تغییر نمی‌دهد؟

چون خروجی جدید ممکن است از نظر تغییرات قابل‌اعمال تفاوتی با وضعیت قبلی نداشته باشد. React در Render تغییرات لازم را مشخص می‌کند.

چرا log گرفتن در بدنه کامپوننت معیار دقیقی برای شمارش Commit نیست؟

چون log در زمان اجرای تابع ثبت می‌شود، نه هنگام Commit. در حالت توسعه و Strict Mode هم ممکن است اجراهای اضافی دیده شوند.

پاسخ‌ها و ارزیابی شخصی: ثبت‌نشده

مسیر چالش‌ها بعد از پایان آموزش

مرحله یک: توضیح مفاهیم با کلمات خودت. مرحله دو: پیش‌بینی خروجی کد و توجیه صف آپدیت. مرحله سه: تشخیص Render اضافی و طراحی بهینه در سناریوی لیست هتل‌ها. مرحله چهار: دفاع از تصمیم فنی، بدون حفظ‌کردن جواب.

وضعیت فعلی: هنوز مصاحبه را آغاز نکرده‌ایم. وقتی گفتی مبحث روشن است، سؤال‌ها را یکی‌یکی مطرح می‌کنیم و پاسخ‌های واقعی تو در این بخش ثبت می‌شود.

خلاصه مخصوص مسیر رفت‌وآمد

React دو کار متفاوت انجام می‌دهد: ابتدا UI مورد نیاز را محاسبه می‌کند و سپس، در صورت نیاز، تغییرات را روی DOM اعمال می‌کند. این تفاوت همان مرز بین Render و Commit است. پس هر بار که کامپوننت اجرا شد، نباید نتیجه بگیریم صفحه حتماً تغییر کرده.
